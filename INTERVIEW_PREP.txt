IMPACTLENS INTERVIEW PREPARATION

SECTION A: PROJECT EXPLANATION

ImpactLens is a local evidence-grounded software change impact analysis system. It ingests repository source and engineering documents, performs Python AST analysis, builds SQL-backed relationships, retrieves relevant evidence with dense and sparse search, and generates structured PR, RAG, and incident outputs.

It solves the problem of fragmented engineering knowledge. A change can affect code, tests, architecture notes, incidents, and historical decisions. Generic code search finds text; a generic chatbot is not tied to repository state and can hallucinate dependencies. RAG retrieves current repository evidence. Graph relationships add statically detectable context. The ML component is intentionally absent until real labelled data exists.

30-second explanation: "ImpactLens ingests a repository, extracts Python symbols and relationships, builds an incremental evidence index, retrieves code and documents using BM25 plus embeddings, and creates cited, uncertainty-aware impact summaries. It also provides incident investigation and a demo PR workflow."

1-minute explanation: "The backend is FastAPI, metadata is SQLite, source is chunked by Python and document structure, and AST analysis extracts stable symbols, imports and direct calls. Retrieval combines cosine similarity over deterministic hash vectors with BM25 and Reciprocal Rank Fusion. A bounded graph traversal supplements evidence. The offline provider formats retrieved evidence instead of pretending to be an LLM, and it abstains with no evidence. GitHub webhook signatures are HMAC-verified. A trained risk model is not claimed because no valid label data exists."

3-minute explanation: "The system separates ingestion, static analysis, retrieval, report assembly, incidents and optional integrations. Incremental indexing hashes source documents and preserves versions. Python AST parsing identifies modules, classes, functions, imports and direct calls. Relationships are labelled static and preserve evidence source and extraction method. Retrieval has dense and sparse rankings. RRF combines ranks without comparing incompatible scores. The evidence builder can return graph neighbors. RAG output includes file and source citations and rejects unsupported output by no-evidence abstention. The current offline provider is deterministic; a hosted LLM can be represented by a provider interface but is not configured. ML risk is a fallback status, not a fake score. Tests cover baseline behavior, and synthetic demo data is clearly labelled."

Detailed walkthrough: 1) Register a repository. 2) Index it. 3) Hash documents and create source-aware chunks. 4) Parse Python and store symbols/relationships. 5) Receive a query. 6) Rank chunks with BM25 and offline embeddings. 7) Fuse rankings with RRF. 8) Optionally traverse the graph. 9) Assemble evidence. 10) Return an answer or report. 11) For PR workflows, accept PR metadata locally and use retrieved evidence plus uncertainty. 12) For incidents, retrieve similar code and historical records but label hypotheses as hypotheses.

SECTION B: PYTHON AND SOFTWARE FUNDAMENTALS

Functions: Python functions implement retrieval, ingestion and API behavior. Classes: Pydantic and dataclass objects represent models and immutable chunks/results. Type hints: document input/output contracts. Pydantic: validates API request and response schemas. Exceptions: convert invalid paths, Git failures and missing configuration into explicit failures. Context managers: SQLite connections are opened and closed in try/finally. Comprehensions: filter files and transform rankings. File handling: repository discovery and UTF-8 reads. JSON: webhook and API payload parsing. HTTP: FastAPI and urllib for local/GitHub requests. Async/await: FastAPI webhook reading is asynchronous. Decorators: FastAPI route decorators register endpoints. Environment variables: configuration and secrets. Logging: the project has explicit status/error fields; centralized structured logging remains limited. Git operations: subprocess executes fixed `git diff` arguments. SQLite: structured metadata and transactions. No inheritance is required in the main implementation.

SECTION C: MACHINE-LEARNING FUNDAMENTALS

Supervised learning learns patterns from labelled examples. Feature is an input such as diff size or test distance. Label is an outcome such as regression observed. Training and testing measure separate populations. Temporal validation prevents future evidence from leaking into training. Overfitting learns noise. Underfitting misses signal. Data leakage uses unavailable-at-prediction information. Precision is the fraction of positive predictions that are correct. Recall is the fraction of real positives found. F1 balances precision and recall. PR-AUC summarizes ranking over many thresholds and is useful for rare positive events. Calibration asks whether a score is a true probability. Confusion matrices expose true/false positive/negative counts. Logistic Regression provides a calibrated linear baseline. Random Forest captures non-linear interactions. The project does not train or claim these models. Accuracy is insufficient for rare incidents because predicting all negatives can score highly while finding no incident.

SECTION D: DEEP-LEARNING AND EMBEDDINGS FUNDAMENTALS

A neural network transforms inputs through learned parameters. An embedding is a fixed vector representing an item. Tokenization divides text; ImpactLens's offline embedder instead uses regular-expression tokens and hash buckets. Cosine similarity measures vector direction. Model inference applies learned or deterministic transformations. CPU and GPU differ in execution hardware. Hugging Face models are approved but not loaded by the current implementation. Embeddings support retrieval; an LLM provider supports generation. ImpactLens embeddings and generated text have separate roles.

SECTION E: RAG FROM FIRST PRINCIPLES

RAG means retrieve relevant context and use it to ground a response. Pretraining is fixed and cannot know repository changes. Ingestion discovers files and documents, chunking preserves source boundaries, and metadata preserves traceability. Embeddings make semantic ranking possible. SQLite stores chunks and metadata. BM25 is sparse lexical retrieval. BM25 score is based on term frequency, inverse document frequency, and document length. Hybrid retrieval combines complementary dense and sparse evidence. RRF sums 1/(60+rank) for each document across rankings. Example: document A ranks 1st and 3rd, while B ranks 2nd; RRF A = 1/61+1/63 > B=1/62. Context assembly selects ranked evidence. Citation validation compares response labels to evidence labels. Abstention occurs when no evidence exists. Recall@K asks whether relevant evidence is in top K. Faithfulness asks whether claims are supported. No actual gold set means no invented retrieval metrics.

SECTION F: GRAPH AND STATIC ANALYSIS

An AST is a syntax tree. ast.parse produces nodes with positions. A symbol is a class, function, method or module identifier. Imports represent module dependency statements, calls represent statically detectable name or attribute calls, and edges represent relationships. Nodes include repository, file, module, class, function, test and documents. Traversal is bounded to avoid cycles. Direct relationships come from AST; indirect relationships are reached through multiple edges. Dynamic dispatch, reflection and dependency injection can hide runtime edges. Static relationship is evidence, not proof of runtime execution.

Example: src/payment.py imports calculate_tax from src/billing.py. PaymentProcessor.charge statically calls calculate_tax. test_payment.py statically references PaymentProcessor and charge. A graph can reach the test. It still does not prove a runtime path in every environment.

SECTION G: APIs, BACKEND AND DATABASES

REST maps operations to HTTP methods. GET reads, POST creates/actions, 422 means invalid input, 401 means authentication failure, 503 means unavailable configuration, 404 means missing repository. FastAPI dispatches typed endpoints. Pydantic validates payload shape. Uvicorn serves ASGI. SQLite tables use primary keys, unique repository IDs, foreign-key document links, and indexes on chunk and relationship fields. Transactions commit index updates together. Chroma is a possible future option but is not used by the current implementation. SQLite stores source, metadata, chunks, and relationships.

SECTION H: GITHUB INTEGRATION

Git tracks snapshots and diffs. A repository has commits and branches. A PR compares base and head SHAs. Connected GitHub repositories support read-only PR diff retrieval; the webhook signature prevents unsigned tampering. HMAC-SHA256 uses the exact raw body and a secret. Idempotency means repeated delivery should not create duplicate analysis. A GitHub token accesses the REST API. Check Runs, comments, and webhook event processing are not implemented.

Complete PR walkthrough: webhook or local payload -> validate -> identify repository/base/head -> git diff -> AST analyze changed symbols -> retrieve evidence -> traverse graph -> assemble uncertainty -> produce report -> optionally publish only after GitHub confirms success.

SECTION I: SYSTEM DESIGN AND PRODUCTION REASONING

The project uses a modular monolith. Indexing is synchronous. Incremental hashing avoids re-embedding unchanged content. No cache or queue is implemented. Idempotency for ingestion comes from content hashes and `INSERT OR REPLACE` behavior. Ingest failures mark status failed and preserve explicit errors. Missing evidence leads abstention. Scaling is limited by in-memory BM25 and dense ranking and SQLite; millions of files require batching, persistent vector storage, a robust graph store, and a queue. Docker and GitHub Actions are included.

SECTION J: EVALUATION AND RESEARCH REASONING

Create a gold dataset by manually labelling relevant chunks for questions. Recall@K = relevant retrieved / relevant total. Precision@K = relevant retrieved / K. MRR = 1/rank of first relevant result. nDCG weights ranking quality by graded relevance. Faithfulness asks whether each claim follows evidence. Citation precision is supported cited claims / citations. Citation completeness is required facts that received citations / required facts. Baselines should include BM25-only and dense-only. No synthetic metric is presented as production performance.

SECTION L: DIFFICULT INTERVIEWER CHALLENGES

Why RAG instead of fine-tuning? Retrieval reflects changing code and supplies citations; fine-tuning is expensive and poor for exact repository versions.
How prevent hallucinated dependencies? Clearly label static evidence, cite retrieved chunks, abstain, and never call graph results runtime proof.
What if the index is stale? Report status and SHA/version metadata and trigger re-indexing.
What if a function is dynamically imported? AST cannot prove the target; report unsupported or uncertain.
What if a model predicts wrong tests? It should be advisory and measured against temporal regression outcomes.
How evaluate rare incidents? Use PR-AUC, recall at a chosen threshold, temporal folds and avoid accuracy-only claims.
How prevent data leakage? Snapshot features at change time and create labels only from later outcomes.
How know calibration? Compare predicted bins to observed regression rates on held-out temporal data.
What happens if GitHub is unavailable? PR analysis returns an explicit gateway error; it never claims Check Run/comment publication.
How handle prompt injection? Treat source as untrusted content and keep system instructions separate in a future hosted provider.
What for millions of files? Incremental batching, persistent vector and search infrastructure, queueing and caching.
What are the limitations? Static-only evidence, hash embeddings, offline generation, no ML labels, no real benchmark and no production GitHub publishing.
What did you implement yourself? The ingestion, AST, graph, BM25, RRF, offline RAG, API, tests, workflows and documentation described in this file.

SECTION N: HONEST PROJECT DEFENCE

Implemented and tested: health/API, SQLite, incremental ingestion, AST, relationships, BM25, hash embeddings, RRF, RAG abstention, PR/incident output, webhook verification and tests.
Implemented but not fully evaluated: graph traversal, end-to-end UI, and retrieval quality; the evaluation script is only a smoke test.
Configured but not production-validated: Docker deployment. GitHub Actions runs the test suite.
GitHub access is bounded and read-only; live PR diffs are fetched for connected repositories, but webhook signatures are only verified, events are not processed, and Check Runs/comments are not published.
Not implemented: trained ML, active Chroma retrieval, hosted LLM, reranker, MLflow, and a benchmark gold set.
Real-world risk prediction and retrieval metrics require labelled outcomes and an externally supplied gold set.
Synthetic demo data must never be described as real company incident evidence.
The project is suitable as an interview/demo engineering implementation, not as a claim of production safety or complete dependency coverage.
